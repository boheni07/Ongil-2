> 작성 2026-07-18 · 참석: PM·PL + CTO팀 10인(아키텍처·DB·SW시니어·UIUX·프론트엔드·백엔드·보안·QA) + 사용자 그룹 12인(6개 역할 × 2명)

## 0. 개최 배경 및 방식

지난 UIUX 워크숍(docs/10)은 로그인 후 웹 화면의 시각 디자인만 다뤘다. 이번 세션은 다음 3가지를 이유로 범위를 확대했다:
1. **모바일이 이번 UIUX 개선(Wave UI-1~4)에서 완전히 제외됐다** — 웹에는 elevation·accent·모션을 적용했지만 모바일 코드베이스 전체에 `shadowColor`/`elevation` 사용이 **0건**으로 확인돼, 웹·모바일 간 시각 격차가 오히려 벌어졌다.
2. **기능 격차도 남아있다** — 웹에 신설한 알림함(`/notifications`)이 모바일엔 대응 화면이 아예 없다(화면 수는 51:51로 동일하지만 최근 신설 기능은 모바일이 못 따라간 상태).
3. `docs/09-cto-team-gap-analysis.md`의 **Wave D(E2E 스팟체크·OAuth·학대신고)가 여전히 미착수**다 — 이번 세션에서 별도 트랙으로 미룬 이유가 여전히 유효한지 재검토가 필요하다.

PM과 PL이 전체 시스템(도메인 6개·역할 6개·record_type 16종·RLS 정책·모바일 파리티 현황)을 시연하고, CTO팀 10인이 각자 분야에서 코드·정책을 직접 검토하며, 6개 역할 × 2명(총 12명)의 사용자 그룹이 실사용 관점에서 피드백을 낸 뒤, 전체가 토론해 우선순위를 정하고 CTO팀이 기술 타당성을 검증해 "대폭 개선계획"을 확정하는 순서로 진행했다.

## 2. PM·PL 시연

## 3. CTO팀 분야별 검토

### 아키텍처전문가
- 웹·모바일 화면 수는 51:51로 맞아떨어지지만, **"화면이 있다"와 "그 화면이 최신 개선을 반영했다"는 별개**라는 점을 이번에 처음 공식적으로 지적. "매 웹 전용 UIUX/기능 라운드가 끝날 때마다 모바일 동기화 여부를 체크리스트화해야 한다"고 제안.

### DB전문가
- 백엔드 actions.ts 전반의 반복문(`for`/`.map(async`) 26곳을 스팟체크 — 대표 사례(`persons/[id]/permissions/actions.ts`)를 직접 확인한 결과 **단일 쿼리 후 JS 메모리 내 매핑**(N+1 아님)으로 확인. "성능 문제는 아니다, 오탐"으로 결론. 이번 세션에서 유일하게 "결함 없음"으로 종결된 항목.

### 보안전문가
- `docs/09` Wave D-2(카카오/네이버 OAuth)가 설계 확정(2026-07-15) 이후 3일 넘게 구현 착수가 안 된 상태 재확인. "설계가 오래 묵으면 그 사이 의존 라이브러리·API 버전이 바뀔 위험이 있다"며 우선순위 상향을 제안.
- 이번 세션에서 실 사용자 12명이 각자 계정으로 접속하는 만큼, 라이브 세션 중 실제 로그인 트래픽으로 **RLS 회귀 여부를 자연스럽게 재검증**할 좋은 기회라고 언급 — 별도 테스트 없이 정상 동작 확인(사용자 그룹 섹션 참조).

### 품질관리자(QA)
- **Claude-in-Chrome 브라우저 자동화 페어링이 이번 세션까지 3회 연속 불안정**했던 것을 정식 이슈로 격상 제안: "Wave D-1(E2E 스팟체크)이 매번 이 문제로 막힌다. 테스트 인프라 자체의 문제이지 회귀할 때마다 재시도할 사안이 아니다." → 로컬 재현 가능한 대체 수단(Playwright 등 자체 관리 브라우저) 검토를 별도 항목으로 제안.
- 12명 사용자 테스트를 곧 pgTAP·타입체크 외의 "제3의 검증 축"(실사용자 QA)으로 공식화하자고 제안 — 매 대형 기능 라운드마다 역할별 2명 이상 핸즈온을 표준 절차화.

### 프론트엔드개발자
- 모바일 elevation 부재는 "Wave UI가 애초에 웹 전용으로 스코프된 것"이라 결함이 아니라 **미착수 항목**이라고 명확히 함(도구 부족: 에뮬레이터 없이 RN 그림자 튜닝 불가하다는 기존 판단 재확인). "모바일 쪽은 실기기/에뮬레이터 접근이 생기는 다음 세션까지 대기가 합리적"이라는 입장.

### 백엔드개발자
- 모바일 알림함 부재는 다르다 — "이건 그림자처럼 시각적 판단이 필요한 게 아니라 `/notifications`의 `getNotifications`/`markNotificationRead` 로직을 그대로 포팅하면 되는 순수 기능 이식"이라 이번에 바로 착수 가능하다고 판단.

### UIUX전문가
- 사용자 그룹 피드백(§4)을 취합하며 "이번엔 신입 vs 숙련, 자녀 1명 vs 다자녀처럼 동일 역할 내에서도 사용 패턴이 다른 사용자를 넣은 게 주효했다 — 똑같은 화면을 보고도 완전히 다른 요구가 나왔다"고 총평.

### SW시니어개발자
- 코드 전반의 아키텍처 패턴(도메인 스코핑 쿼리, `logAccess` 재정의 관행 등)이 이번 12명 규모 테스트에도 무너지지 않고 버틴 것을 확인 — "기존에 쌓아온 패턴 재사용 원칙(YAGNI, 4번째 사례 시 재논의)이 유효했다"고 긍정 평가.

## 5. 토론 및 협의

- **모바일 알림함 이식은 이견 없이 최우선 합의** — 순수 기능 이식이라 리스크 낮고, 당사자 A의 피드백과도 직결.
- **모바일 elevation/모션은 이번 라운드에서 착수하지 않기로 합의** — 실기기/에뮬레이터 없이 진행 시 오히려 잘못된 값(그림자 방향, 강도)을 넣을 위험이 크다는 프론트엔드개발자·QA 공동 의견. 대신 "다음 세션에 에뮬레이터/실기기 접근이 확보되면 최우선 착수"로 조건부 예약.
- **Claude-in-Chrome 페어링 불안정 이슈**는 QA가 제기했지만 이 세션에서 즉시 해결할 수 있는 사안이 아니므로(외부 도구 문제) 별도 이슈로만 기록, 대체 수단 검토는 후속 세션 안건으로 분리.
- **EDU-005(ITP) 당사자 열람권 확인**은 사용자 B의 관찰이 실제 RLS/화면 갭인지 오탐인지 확인이 우선이라는 데 합의(설계상 ITP는 학교-보호자 중심 문서라 당사자 열람이 원래 범위 밖일 수도 있음 — 판단 전 코드 확인 필요).
- **PersonSlider 3명+ 그리드 뷰**, **특수교사 학생 목록 ITP 대상 배지**, **사회복지사 LEG/사례회의록 통합 진입점**은 전부 소규모 UI 추가라 우선순위는 낮지만 다음 UIUX 라운드에 함께 처리하기로 합의.
- **Wave D-2(OAuth) 우선순위 상향**은 보안전문가 의견대로 채택 — 설계 확정 후 방치 기간이 길어질수록 리스크가 커진다는 데 전원 동의.

## 6. CTO팀 기술 협의 결과 — 검증

토론에서 나온 "확인 필요" 항목을 CTO팀이 즉시 코드로 검증했다(추측으로 개선계획에 넣지 않기 위함).

**EDU-005(ITP) 당사자 열람권 확인** (백엔드개발자 실측):
- `records_select` RLS는 `record_type`을 구분하지 않고 `domain`(EDU) 단위로만 판정하며, person 셀프 분기(`auth.uid()=persons.id`)는 도메인·record_type 무관하게 본인 관련 모든 기록에 적용된다.
- 즉 **당사자 B가 청소년 전환기 자기 계정으로 로그인하면 ITP를 포함한 자기 EDU 기록을 볼 권한 자체는 이미 있다.** 다만 이는 어디까지나 person 역할로 셀프 로그인한 경우의 얘기이고, B는 "보호자가 대리 시연"한 상황이라 실제로 본인 계정으로 접속해보지 않았을 가능성이 크다.
- **결론: RLS/기능 결함이 아니라 UX 발견성(discoverability) 문제** — 당사자 모드(P-10 내 기록 보기)에 ITP가 다른 EDU 기록과 함께 표시되긴 하지만, 청소년 전환기 당사자가 이 화면 자체를 찾기 어려울 수 있다는 점이 진짜 이슈로 재정의됨.

- `pnpm --filter @ongil/mobile typecheck` 통과.

### Wave M-2: 당사자 ITP 발견성 개선 — ✅ 완료(2026-07-18)
- P-10(당사자 내 기록 보기, 웹 `PersonRecordsView.tsx`·모바일 `MyRecordsScreen.tsx`) 목록 최상단에 조건부 안내 배너 추가: `lifeStage === "youth_transition"` 이고 목록에 `recordType === "EDU-005"`가 하나라도 있으면 "🎓 학교에서 준비한 개별화전환계획(ITP)이 있어요. 아래 목록에서 확인해 보세요." 표시.
- RLS·백엔드 변경 없음(§6에서 이미 정상 확인) — 순수 발견성(discoverability) UX 개선.

### Wave M-3: 소규모 UI 보완 묶음 — ✅ 완료(2026-07-18)
- **PersonSlider 3명+ 그리드 뷰**: 카드 렌더링을 `PersonCard` 컴포넌트로 추출해 슬라이더/그리드 양쪽에서 재사용. 3명 이상일 때만 우측 상단에 "⊞ 그리드로 보기" 토글 노출, 그리드 모드는 `grid-cols-1 sm:grid-cols-2 lg:grid-cols-3`로 전원 동시 표시.
- **TeacherHome ITP 대상 배지**: 기존 "전환계획 수립 대상"(13세+ 전체) 배지와 별개로, `isItpActiveStage`(청소년 전환기만)로 좁힌 "🎓 ITP(개별화전환계획) 대상" 배지 추가 — 웹·모바일 동시 구현(모바일은 학생 카드 우측에 `DOMAIN_COLORS.EDU` 톤 태그).
- **SocialWorkerHome LEG/사례회의록 통합 진입점**: 웹은 새 `CaseManagementMenu`(base-ui DropdownMenu 재사용) 클라이언트 컴포넌트로 두 버튼을 하나의 드롭다운("📁 법률·복지 기록 관리 ▾")으로 합침 — `SocialWorkerHome.tsx`가 Server Component라 드롭다운 자체는 별도 `"use client"` 파일로 분리해야 했음. **모바일은 변경하지 않음** — 두 버튼이 이미 같은 행(`newRow`)에 나란히 배치돼 있어 "따로 놀던 진입점" 문제가 웹만큼 심하지 않다고 판단(RN에 base-ui 동급 드롭다운 프리미티브가 없어 억지로 만들면 배보다 배꼽이 큼).

- Wave M-5 착수 전 재확인: 실기기/에뮬레이터 접근이 여전히 없어 shadow/elevation 값을 추정으로 채우면 오히려 틀릴 위험이 크다는 기존 CTO팀 판단을 그대로 유지. 사용자에게 이 결정을 구두로 명시적 고지한 뒤 M-5로 넘어감(침묵 스킵 아님).

### Wave M-5: OAuth 구현 우선순위 상향 (기존 Wave D-2 승격) — ✅ 코드 구현 완료(2026-07-18), 라이브 검증은 자격증명 확보 전까지 불가
- DB: `AuthProvider` enum(`email`/`kakao`/`naver`) + `users.auth_provider`/`oauth_subject`/`email_verified` 3컬럼 + `(auth_provider, oauth_subject)` UNIQUE + partial index 마이그레이션. `handle_new_user()` 트리거를 OAuth 메타데이터도 읽도록 갱신 — role 메타데이터가 없는 신규 OAuth 유저는 `public.users` 행 생성을 의도적으로 건너뛰고 `/signup/oauth-complete`에서 역할 선택 후 완성하는 흐름(기존 "안전장치" 설계 재사용). 두 마이그레이션 모두 `prisma migrate deploy`로 적용, `BEGIN...ROLLBACK` 트랜잭션 안에서 기존 이메일가입 경로·신규 OAuth 경로 양쪽을 직접 INSERT해 트리거 동작을 실측 검증.
- 컬럼 GRANT 재검토: 신규 컬럼 3개가 테이블 단위 GRANT를 상속해 `authenticated`에 SELECT+INSERT가 부여됨을 확인했으나, `users`에는 애초에 INSERT RLS 정책이 전혀 없어(2026-07 초 `p3_users_column_grant_hotfix` 이후 UPDATE만 컬럼 단위로 제한) RLS가 INSERT를 기본 전면 차단 — 신규 취약점 아님을 라이브 쿼리로 확인.
- 백엔드: 카카오·네이버 둘 다 Supabase 네이티브 provider가 아닌 동일한 커스텀 OAuth2 Authorization Code 브리지로 구현(카카오도 OIDC/`signInWithIdToken` 대신 이 패턴 채택 — GoTrue 버전에 의존하는 불확실한 설정 없이 완전히 자체 검증 가능하게 하기 위함, `oauth-bridge.ts` 상단에 이 설계 결정과 "라이브 미검증" 경고를 명시). `/api/auth/{kakao,naver}`(인가 요청, state CSRF 쿠키) + `/api/auth/{kakao,naver}/callback`(코드 교환·프로필 조회·`completeOAuthCallback` 위임) 4라우트, 공용 로직은 `oauth-bridge.ts`(계정 매칭 → 세션 수립(magiclink+verifyOtp 브리지) → 기존 이메일가입 계정과 이메일 충돌 시 계정탈취 방지 안내 → 신규 시 role 없이 `admin.createUser()` 후 온보딩 리디렉션).
- 프론트: `SocialAuthButtons`(카카오 `#FEE500`/네이버 `#03C75A`, `docs/03-uiux.md` §6-8 스펙 준수) `/login`·`/signup`에 추가, `/signup/oauth-complete` + `OAuthCompleteForm`(역할선택+동의, 프로필 필드는 생략) + 서버 액션 `completeOAuthSignup`(`(auth)/actions.ts`, 멱등 가드 포함) 신설.
- **실측으로 발견·수정한 실버그**: `origin`을 `Origin` HTTP 헤더에서 구하던 최초 구현이 일반 GET 네비게이션(링크 클릭)에는 그 헤더가 전송되지 않아 4개 라우트 핸들러 전부에서 500 에러(`ERR_INVALID_URL`)를 실제로 재현·확인 — `req.nextUrl.origin`(요청 URL 자체)으로 교체해 전부 수정. 수정 후 `pnpm --filter @ongil/web typecheck`·`build`(48라우트 전체 생성 확인) 통과, 로컬 dev 서버를 띄워 `/api/auth/kakao`·`/api/auth/naver`를 실제로 curl해 자격증명 미설정 시 500이 아닌 307(`/login?error=...`) 정상 리디렉션을 확인, `/login?error=...`가 `<Suspense>`로 감싼 `OAuthErrorBanner`를 통해 실제로 렌더링되는 것도 확인.
- **한계**: 카카오/네이버 개발자센터 앱 등록은 플랫폼 소유자만 할 수 있는 외부 작업이라 이 세션에서 수행 불가 — 따라서 실제 토큰 교환·프로필 조회·계정 생성까지 이어지는 end-to-end 로그인은 라이브 검증되지 않았다. `apps/web/.env.local`에 필요한 4개 환경변수(`KAKAO_CLIENT_ID` 등)와 가입 절차 안내를 주석으로 남겨둠 — 사용자가 실 자격증명을 채워 넣은 뒤 별도 라운드에서 재검증 필요.
- 담당: 백엔드개발자·보안전문가.
