# UIUX 워크숍 13 — 역할별 "당사자 선택" 방식 교차 검토

**일자:** 2026-07-20
**참석:** 기술팀(전문가 4명 — PM, UIUX 리드, 프론트엔드 시니어개발자, 접근성 전문가) + 사용자팀(페르소나 4명 — 다자녀 보호자, 특수교사, 사회복지사, 활동지원사)

**범위:** 코드 변경 없음 — 이번 라운드는 조사·토론·개선 로드맵 수립까지만.

## 1. 사전 조사 (근거 확보)

착수 전 3개 병렬 조사를 수행했다(코드 리딩 전용, 변경 없음):

- **조사 A** — 4개 전문직군(교사·사회복지사·치료사·지원사)의 Home→작성화면→타임라인 이동 경로에서 "담당 당사자 선택"이 몇 번 반복되는지
- **조사 B** — 보호자 웹/모바일에서 직전 세션에 도입한 `CurrentPersonProvider`(헤더 콤보박스↔사이드바↔PersonSlider 공유 상태)가 실제로 어디까지 일관되게 동작하는지
- **조사 C** — 당사자(person) 모드 + 전 역할 공통 UI(헤더/사이드바/탭바/알림/설정)의 일관성

### 조사 A 요약 — 전문직군: 전역 "현재 학생" 상태 없음

`apps/web/src/app/(app)/layout.tsx:136`은 `role === "guardian"`일 때만 `CurrentPersonProvider`로 분기하고, 나머지 4개 전문직군은 정적 `Sidebar`(공유 상태 없음)로 떨어진다.

| 화면 | Web | Mobile |

| Home → 작성화면(정식 위자드류: IEP/ITP/치료계획/ISP/전환/BIP/평가/사례회의/후견보고/상담) | **매번 다시 고름** — `initialPersonId`가 있어도 `<select>`가 항상 렌더됨(`IepWizard.tsx:214-224` 등) | **유지됨** — `paramPersonId` 있으면 선택 UI를 숨기고 배너만 표시(`IepWizardScreen.tsx:316` 등) |

**시나리오 재현** — 특수교사가 학생 A의 IEP 확인→관찰기록 작성→타임라인 확인:
- 웹: Home 카드 클릭(1차)→IEP(프리필되지만 select 노출)→관찰기록은 Home에서 personId 없이 진입해 **2차 재선택** 필요→저장 후 타임라인은 자동 이동(재선택 면제)이나, Home에서 곧장 타임라인으로 가면 **3차 재선택**.

### 조사 B 요약 — 보호자: 웹은 되고, 모바일은 격차 뚜렷

웹은 직전 세션에 도입한 `CurrentPersonProvider`(`apps/web/src/components/guardian/CurrentPersonProvider.tsx`)로 헤더 콤보박스·사이드바(`GuardianSidebar.tsx`)·대시보드 `PersonSlider`가 같은 상태를 공유해, 한 번 고른 당사자가 화면을 옮겨도 유지된다. 다만 `persons/[id]/records/new` 이후 경로는 URL 파라미터로 이어지는 별개 경로라 "선택 소스가 Context와 URL 두 개"라는 점은 유의 대상.

모바일은 `GuardianDashboardScreen.tsx:27`의 `selectedId`가 로컬 `useState`이고, 하단 탭(타임라인/기록/권한)이 `PersonPickerScreen`을 매번 거치게 되어 있어 **대시보드에서 이미 고른 당사자가 하단 탭 이동 시 사라진다** — 웹의 헤더 콤보박스에 대응하는 전역 선택 UI가 모바일엔 없음. 다자녀 그리드뷰 토글(웹 `PersonSlider.tsx:127`, 3명 이상 시 노출)도 모바일 대시보드엔 없어 인원이 많아질수록 스캔 효율 격차가 커진다. `StageBadge`도 웹 카드에만 있고 모바일엔 "성년" 텍스트 태그로 축약돼 정보 밀도가 낮다.

### 조사 C 요약 — 당사자 모드·공통 UI

당사자 모드는 사이드바 없는 단일 컬럼(웹 `layout.tsx:117`)에 큰 CTA·타일 중심으로 WCAG 큰 터치타겟 원칙을 의식적으로 지키고 있다(`PersonHome.tsx:69-71` 주석: "축소하지 않는다"). 다만 Wave P-4(모바일 하단 탭바)가 당사자 역할만 제외해(`RoleTabNavigators.tsx:31-40` 주석) 알림 접근이 다른 역할(탭바+공통 벨아이콘)보다 오히려 한 단계 더 깊다(홈 화면까지 가서 버튼 선택). 사이드바(전문직군, 서버 컴포넌트 정적 구성)와 탭바(모바일) 항목 수가 역할마다 불일치하고("IEP 점검"·"타임라인"이 교사 탭바에서 빠짐 등), 보호자만 "설정"이 "동의·권리 관리"로 라벨이 다르다.

## 2. 토론

**PM (진행):** PO 가설부터 짚자. "보호자=당사자 중심 / 전문직군=업무 중심으로 당사자를 고르는 방식"이 편의성이 높겠다는 의견인데, 조사 A·B를 보면 이미 코드가 그 방향으로 짜여 있다 — 전문직군엔 애초에 전역 Context가 없다. 그럼 오늘 논점은 "이 설계 방향이 맞냐"가 아니라 "이 방향 안에서 실행이 매끄러운가"다.

**UIUX 리드:** 동의한다. 다만 "업무 중심으로 당사자를 선택"이 곧 "매번 처음부터 목록을 뒤진다"를 의미하면 안 된다. 조사 A의 시나리오 재현을 보면 특수교사가 같은 학생을 두고 세 번씩 다시 고른다 — 이건 "업무 중심"이 아니라 그냥 "선택 상태가 없는" 것이다. 업무 중심이라면 오히려 "지금 보고 있는 사례를 방금 봤던 목록 맨 위에 띄워주는" 정도의 배려가 있어야 한다.

**특수교사 페르소나:** 정확히 그거다. 학생 A 관찰기록 쓰다가 같은 애 IEP 확인하려고 다시 학생 목록에서 찾는 게 하루에도 여러 번이다. 완전히 자동으로 고정해달라는 게 아니라, 방금 본 학생이 목록 맨 위나 기본 선택값으로 와 있으면 충분하다.

**사회복지사 페르소나:** 나는 오히려 "고정"에는 반대다. 하루에 사례 여러 건을 오가며 처리하는데, 화면 전환할 때마다 이전 사례 화면이 남아있으면 실수로 다른 사람 기록에 잘못 쓸까 걱들었다. "매번 고른다"는 자체가 확인 절차로 기능하는 면도 있다.

**활동지원사 페르소나:** 사회복지사님 의견에 공감한다. 나는 방문 순서대로 3~4명을 오가는데, 목록에서 매번 고르는 행위 자체가 "지금 내가 누구 집에 있는지" 재확인하는 안전장치처럼 느껴진다. 다만 목록에서 찾는 속도는 빨랐으면 좋겠다 — 이름 순서가 뒤죽박죽이면 매번 스크롤한다.

**프론트엔드 시니어개발자:** 그럼 결론은 "강제 고정(보호자식 Context)"이 아니라 "최근 선택을 힌트로만 주는 가벼운 상태"로 가는 게 맞겠다. 구현 관점에서도 그게 낫다 — 보호자처럼 헤더·사이드바·슬라이더 세 곳을 하나의 Context로 강하게 묶는 건 "이 세션 동안 보는 대상이 거의 고정"인 보호자 UX엔 맞지만, 전문직군은 애초에 여러 대상을 넘나드는 게 정상 업무 흐름이라 그 정도로 강하게 묶을 필요가 없다. 로컬스토리지/세션 수준의 "최근 선택 N명" 힌트 정도로 충분하다.

**접근성 전문가:** 안전장치 얘기가 나온 김에 — 지금 웹은 폼 진입 시 select가 항상 노출돼 있어서 "누구 기록인지 저장 직전에도 눈으로 확인 가능"한 게 오히려 장점일 수 있다. 모바일처럼 선택 UI를 아예 숨기고 배너 텍스트만 주는 방식은 화면을 대충 보고 넘기는 사용자에게는 "확인 절차 생략"으로 이어질 위험이 있다. 활동지원사님이 말한 "재확인이 안전장치"라는 지적과 같은 맥락이다 — 없애기보다 "제출 직전 대상자 재확인 배너"를 명확히 강조하는 방향이 낫다.

**다자녀 보호자 페르소나:** 나는 반대로 웹은 이제 정말 편해졌다. 헤더에서 아이 하나 고르면 사이드바고 뭐고 다 그 아이 걸로 딱 맞춰진다. 근데 앱(모바일)은 대시보드에서 골라놓고 하단 탭에서 "기록" 누르면 또 목록부터 나온다. 왜 웹이랑 다른가 싶다.

**PM:** 보호자는 웹·모바일 UX 패리티가 명백한 결함이니 최우선으로 정리하자. 전문직군은 오늘 토론으로 방향이 잡혔다 — "강제 유지"가 아니라 "최근 선택 힌트 + 제출 직전 재확인"의 하이브리드.

**UIUX 리드:** 그리고 부수적으로 나온 것들 — 사이드바/탭바 항목 수 불일치, 당사자 모드 알림 경로, 다자녀 보호자 모바일 그리드뷰 부재도 이번에 정리하자. "설정" 라벨은 보호자만 다른 게 의도된 설계(동의·권리 관리는 실제로 다른 기능 묶음)라 굳이 통일할 필요는 없다는 데 다들 동의하는지?

**(전원 동의 — 라벨 차이는 결함이 아니라 의도된 설계로 결론.)**

## 3. 결론 — 사용자 가설에 대한 UIUX팀 검토 의견

> **PO 가설("보호자=당사자 중심 / 전문직군=업무 중심 선택")은 방향성 자체는 맞다** — 이미 코드 구조가 그렇게 갈라져 있고(보호자만 전역 Context), 사회복지사·활동지원사 페르소나도 "매번 고르는 게 오히려 안전하다"고 명시적으로 지지했다. **다만 현재 구현은 "업무 중심"이 아니라 "선택 상태 자체가 없는" 상태에 가깝다** — 같은 화면 체인 안에서도 불필요하게 재선택을 요구하고(관찰기록/타임라인 진입 버튼에 personId 누락), 모바일 탭 전환마다 완전히 리셋된다. **"매번 고른다"의 안전장치 가치는 유지하되, 목록 정렬·최근 선택 프리필로 그 과정을 빠르게 만드는 것**이 이번 워크숍의 핵심 결론이다.

## 5. Q-1 구현 기록 (2026-07-20)

교사/사회복지사/치료사 3개 Home 화면의 담당 학생·당사자 카드에 "관찰기록"(교사)·"회기 일지"(치료사)·"타임라인"(3역할 공통) 퀵링크를 카드 하단에 추가해 `personId`를 함께 실어 보내도록 했다. 카드 전체를 감싸던 `<Link>`를 `<div>`로 바꾸고 내부에 주 액션용 `<Link>`(IEP/ISP/치료계획 상세)를 두어, 하단 퀵링크가 중첩 `<a>`가 되지 않도록 구조를 정리했다.

같은 이유로 이미 특정 당사자가 정해진 상세 화면(`IepReviewPane`·`IspReviewPane`·`TherapyPlanDetail`)에도 "타임라인 보기" 버튼을 추가해, 상세 화면에서 곧장 그 당사자의 타임라인으로 이동할 수 있게 했다(`IepReviewPane`은 관찰기록 작성 버튼도 함께 추가 — 기존엔 참조 패널 안의 "＋ 새 관찰기록 연결"에서만 가능했음).

접근 방식은 토론 결론(§3)을 따랐다 — 재선택 자체를 없애는 게 아니라, "이미 특정 당사자를 보고 있는 화면"에서 관련 화면으로 넘어갈 때만 재질문을 생략했다. Home의 상단 공용 액션 버튼(예: "＋ 새 IEP 작성", "관찰기록 작성" 전역 버튼)은 특정 학생 맥락이 없는 진입점이라 그대로 두었다 — 이건 결함이 아니라 목록 화면의 정상적인 동작이다.

`pnpm --filter @ongil/web typecheck`·`build` 모두 통과.

## 6. Q-4 구현 기록 (2026-07-20)

모바일 보호자 대시보드(`GuardianDashboardScreen.tsx`)의 당사자 슬라이더에 웹 `PersonSlider.tsx`와 동일한 규칙(3명 초과 시에만 노출)의 그리드뷰 토글을 추가했다. 기존엔 인원수와 무관하게 항상 가로 슬라이더만 제공했다(§조사 B 지적).

카드 렌더링을 `PersonCard` 컴포넌트로 추출해 슬라이더(`width: 260` 고정)와 그리드(`flexBasis: "47%"`, 2열) 양쪽에서 재사용한다. 카드 내부의 "성년" 텍스트 태그도 웹과 동일한 `StageBadge`(5단계 생애주기 배지, 아이콘+색상+라벨)로 교체해 웹·모바일 정보 밀도 격차를 해소했다 — `computeLifeStage(p.birthDate)`로 클라이언트에서 직접 계산한다(다른 모바일 화면들의 기존 관행과 동일).

`pnpm --filter @ongil/mobile typecheck` 통과. 에뮬레이터가 없어 실제 그리드 레이아웃 렌더링은 미검증(타입체크로만 확인) — 실기기 확보 시 스팟체크 대상.

## 7. Q-2/Q-3 구현 기록 (2026-07-20, 웹만)

전문직군 대상자 select가 있는 웹 폼 11개(IepWizard·ItpWizard·ObservationForm·BipForm·TherapyPlanWizard·EvalReportForm·IspWizard·TransitionPlanWizard·GuardianshipReportWizard·AdvocacyConsultationForm·CaseConferenceForm) + 목록형 진입 허브 2개(CaseNotesBoard·LegRecordsBoard) 전부에 적용했다.

"")` 초기화 블록을 전부 교체했다. `initialPersonId`가 없을 때만(=Home 상단 공용 버튼처럼 특정 학생 맥락 없이 진입한 경우만) 마운트 후 `useEffect`에서 localStorage(`ongil_recent_person`)의 "최근 선택"으로 기본값을 보정한다 — 초기 렌더는 항상 서버와 동일한 값(첫 번째 항목)으로 시작해 하이드레이션 불일치를 피했다. 선택이 바뀔 때마다 localStorage에 기록해 다음 진입 때도 이어진다.
