# 기록 체계 재설계 워크숍 — 이해관계자 합동 협의록

> 작성일: 2026-07-17 | 최종 갱신: 2026-07-18 | 성격: **합의 결론 문서** — 이 문서의 표(§5, §8)가 실제 반영 대상. 근거: `docs/07-lifecycle-record-permission-proposal.md`(생애주기 5단계), 온길 권한 매트릭스 Artifact(§03 생애주기×기록×이해관계자 전체 권한표, §09 설계 vs 현장 실무 비교, §10 신규 반영 후보 목록 — 전 항목 결론 완료로 갱신됨)
> 방식: PM팀(제품·기술 관점 5인) + 이해관계자(사용자 관점 5인) 합동 협의. 각 안건마다 상충하는 이해관계를 실제로 드러내고, 그 긴장을 어떻게 풀었는지를 남긴다 — 결론만 있고 근거가 없는 문서는 다음 라운드에 같은 논쟁을 반복시킨다.

## 0. 참여자 구성

**PM팀**
| 역할 | 관점 |
|---|---|
| PM (제품 총괄) | 우선순위·일정·"이 기능이 없으면 정말 안 되는가" |
| PL (프로젝트 리드) | 구현 가능성·의존관계·다음 라운드 실행 계획 |
| SW 시니어 개발자 | 구현 복잡도·유지보수 부담·기존 패턴 재사용 |
| UIUX 전문가 | 입력 부담·화면 수·완료까지 걸리는 클릭 수 |
| DB 전문가 | 스키마 정합성·RLS 확장 비용·갱신 주기 불일치 |

**이해관계자**
| 역할 | 관점 |
|---|---|
| 당사자 대표 | 본인 기록의 심리적 부담, 문해력·표현력 편차 |
| 보호자 대표 | 대리 작성 범위, 알림 피로, 여러 자녀·피후견인 동시 관리 |
| 특수교사 대표 | 학교 실무(개별화교육지원팀, ITP)와의 정합성, 학기 중 업무량 |
| 활동지원사 대표 | 현장 기록 속도, 정산 증빙, 스마트폰 입력 환경 |
| 사회복지사 대표 | 사례관리 다건 처리, 타 기관 연계, 법정 서류 기한 |

## 1. 안건 1 — 기존 14종 record_type, 그대로 둘 것인가

**논의**
- UIUX 전문가: "SELF-001은 이미 음성·사진 위주라 당사자 부담이 낮다. 다만 감정 아이콘 4종(good/neutral/sad/angry)이 실제 발달장애 당사자의 정서 표현 폭에 비해 너무 단순하다는 의견이 있었다."
- 당사자 대표: "네 가지로는 부족하다고 느낄 때가 있다. 하지만 선택지가 늘면 오히려 고르기 더 어려워진다 — 지금 개수가 낫다."
- 활동지원사 대표: "DAI-002 계획/실적 시간 구분은 실제로 큰 도움이 된다. 다만 매번 같은 활동 카테고리를 반복 입력하는 게 번거롭다."
- SW 시니어 개발자: "최근 자주 쓴 활동 카테고리를 상단에 노출하는 정도는 스키마 변경 없이 프론트에서만 처리 가능하다."
- 특수교사 대표: "EDU-001/002/003은 학교 실무와 크게 다르지 않다. IEP는 개별화교육지원팀 협의를 거치는데 온길은 내가 혼자 쓰는 것처럼 보일 수 있어 걱정했지만, 실제로는 협의 결과를 옮겨 적는 최종 문서로 쓰면 되니 문제없다."
- 사회복지사 대표: "WEL-004/005를 두 화면으로 나눠 쓰는 게 처음엔 번거로웠는데, 서비스 변경이 잦은 이용자는 WEL-005만 자주 고치고 ISP는 그대로 두는 게 오히려 편했다."
- 치료사 측 의견(사전 서면 의견 취합): "MED-006/007의 domain_scores 4영역 점수는 실무보다 더 정량화돼 있다. 부담은 없지만, 굳이 필수로 강제하면 평가 도구가 없는 영역은 억지로 숫자를 넣게 될 수 있다."

**결론**
- 14종 전부 **기존 유지**. 단 3건의 미세 조정을 다음 라운드 백로그로 등록:
  1. SELF-001 감정 선택지 확장 여부는 이번엔 보류(선택지 증가가 오히려 부담이라는 당사자 의견을 존중) — 대신 `memo`/`voice_url` 자유 표현 경로를 UI에서 더 눈에 띄게 배치.
  2. DAI-002 활동 카테고리 자동완성(최근 사용 항목 우선 노출) — 스키마 변경 없음, 프론트 전용.
  3. MED-006/007 `domain_scores` 필드를 없는 영역은 생략 가능하도록 optional 처리 재확인(이미 Zod 스키마상 배열/선택 구조라 강제성 낮음 — 실제 폼 UI가 "빈칸 두면 안 될 것 같은" 압박감을 주지 않는지 frontend-dev 재점검 권고).

## 2. 안건 2 — 신규 후보 6종, 채택할 것인가

### 2-1. EDU-004(기능행동평가 FBA) — **채택하지 않음, EDU-003에 병합**

- 특수교사 대표: "FBA는 실무에서 분명 중요하다. 하지만 별도 문서로 또 하나를 만들면 BIP 쓰기 전에 항상 FBA부터 완성해야 하는 순서 강제가 생긴다. 학기 중엔 그럴 시간이 없는 경우가 많다."
- PM: "완전히 새 record_type을 만드는 비용 대비, 지금 BIP 안의 `behavior_function` 필드를 조금 더 구조화하는 것으로 실익을 볼 수 있는가?"
- DB 전문가: "새 테이블이 아니라 JSONB 필드 확장이라 마이그레이션 자체는 안 든다. RLS·permission_presets도 건드릴 필요 없다."
- UIUX 전문가: "BIP 위자드에 '기능평가 근거' 선택 단계 하나만 추가하면 된다. 별도 화면·별도 목록을 만들지 않아도 된다."

**결론**: EDU-003(BIP) 스키마에 `fba_basis`(관찰/면담/체크리스트 등 근거 자료 유형, 복수선택) 필드를 **선택적으로 추가**. 별도 record_type(EDU-004)은 **채택하지 않음** — 병합.

### 2-2. EDU-005(개별화전환계획, 학교 ITP) — **신규 채택 (P2)**

- 특수교사 대표: "이건 다르다. IEP의 전환계획 서브섹션은 목표·단계 2줄이 전부라 실제 ITP가 요구하는 진로흥미검사, 현장실습 이력을 담을 곳이 없다."
- 사회복지사 대표: "성인기 이후 내가 TRA-001을 받을 때, 학교에서 뭘 했는지 알 방법이 사실상 없다. 지금은 보호자에게 구두로 듣거나 아예 모른 채 새로 시작한다."
- PM: "새 record_type을 만들 만한 실익이 명확하다. 다만 범위가 커지지 않게 최소 스키마로 시작하자."
- PL: "TRA-001과의 관계는 FK로 엮지 말고 기존 관행대로 `person_id`로만 연결하자 — TRA-001이 EDU-001.transition_plan을 참조하지 않는 것과 같은 패턴이라 일관성이 있다."
- 보호자 대표: "학교 따로, 복지관 따로 서류를 받는 게 제일 피곤했다. 두 기록이 한 타임라인에서 이어 보이기만 해도 큰 도움이 된다."

**결론**: **EDU-005 신규 채택.** 주작성자=특수교사, 활성 시기=청소년기(만 13~18세, TRA-001과 동일 조건), requires_confirmation=true(공식 문서). 스키마는 `career_interest_areas`(흥미영역 체크리스트), `work_experience_log`(현장실습 이력), `next_step_note`(성인기 인계 메모) 최소 3필드로 시작 — PM의 "범위 최소화" 원칙 반영. TRA-001 작성 화면에서 같은 당사자의 최근 EDU-005를 참고용으로 보여주는 **소프트 링크**(FK 아님, person_id 조회) 추가.

### 2-3. WEL-006(사례회의록) — **신규 채택 (P3)**

- 사회복지사 대표: "ISP를 왜 이렇게 세웠는지 나중에 설명해야 할 때가 있다. 회의 논의 과정이 하나도 안 남으면 곤란하다."
- PM: "확인(confirmation) 절차가 또 붙으면 알림 피로만 커진다. 이건 결정 근거를 남기는 로그 개념으로 가자."
- UIUX 전문가: "회의 중에 빠르게 메모하듯 쓸 수 있어야 한다 — 위자드가 아니라 단일 텍스트 폼이 맞다."
- 당사자 대표: "내 얘기를 하는 회의인데 나는 모르고 지나가는 게 걱정된다."
- 사회복지사 대표: "회의록 자체를 당사자에게 확인받는 절차로 만들면 무겁다. 대신 회의록이 저장되면 당사자·보호자에게 '조회 가능' 알림 정도만 가면 충분하다."

**결론**: **WEL-006 신규 채택.** requires_confirmation=**false**(일상기록 취급, 알림 피로 방지 원칙 유지), 저장 시 당사자·보호자에게 일반 알림(notifications, 확인 절차 아님)만 발송. 단일 폼(제목 없이 날짜·참석자·논의내용·결정사항 4필드).

### 2-4. LEG-003(재산목록보고서, 후견개시 초기) — **채택하지 않음, LEG-001에 필드 병합**

- DB 전문가: "LEG-001과 스키마가 90% 겹친다. `report_period`, 요약 필드 구조가 거의 그대로 재사용 가능하다."
- 사회복지사 대표: "완전히 새로운 화면·새로운 배우는 방식이 생기는 것보다, 같은 화면에서 '최초 보고'인지 '정기 보고'인지 고르는 정도가 훨씬 편하다."
- PL: "동의한다. 신규 record_type 대신 판별 필드로 처리하면 RLS·권한 프리셋도 그대로 재사용된다."

**결론**: LEG-001 스키마에 `report_kind: 'initial' | 'periodic'`(기본값 `periodic`) 필드 추가. **별도 record_type(LEG-003) 신설하지 않음** — 병합.

### 2-5. MED-008(발달재활서비스 의뢰서) — **기각**

- 치료사 측 의견: "신청·자격 심사는 지자체·바우처 시스템(사회서비스 전자바우처) 소관이다. 우리가 이걸 또 만들면 이용자는 같은 서류를 두 번 내는 셈이 된다."
- PM: "온길은 '이용 개시 이후' 지원 기록 관리 도구다. 신청 단계까지 흡수하는 건 제품 정체성을 흐린다."
- DB 전문가: "만약 나중에 외부 바우처 시스템과 연동한다면 그건 이 record_type 신설이 아니라 별도 통합(API 연계) 과제다."

**결론**: **기각.** 온길의 스코프(서비스 이용 개시 이후 관리)와 맞지 않음 — 신청 단계는 의도적으로 다루지 않는다는 점을 `docs/01-prd.md`에 명시하기로 함.

### 2-6. 학대의심 신고 에스컬레이션 — **별도 트랙 분리**

- 사회복지사 대표: "LEG-002에 `abuse_suspected`를 고르고 끝나면 안 된다. 실제로는 즉시 신고 의무가 따른다."
- PM: "이건 record_type이 아니라 알림·에스컬레이션 워크플로우다. 지금 이 워크숍의 의사결정 범위를 넘어선다."
- PL: "법적 책임이 걸린 사안이라 법률 자문 없이 자동화 로직부터 만드는 건 위험하다. 사람이 반드시 개입하는 알림 설계부터 시작해야 한다."

**결론**: 기록 목록에서 제외하고 **F-LEG-11 요구사항**(신규)으로 분리 등록. 법률 자문 선행 후 별도 라운드에서 논의.

## 3. 안건 3 — 병합/분리가 애매했던 지점 재확인

### 3-1. WEL-004 vs WEL-005 — 병합 안 함, 화면만 통합

- 사회복지사 대표(초기 입장): "화면을 합쳐주면 좋겠다."
- UIUX 전문가: "화면 수가 줄면 확실히 편하다."
- DB 전문가: "ISP는 분기~반기 단위 재사정이고, 서비스 이용계획은 서비스 변경 때마다 수시로 바뀐다. 합치면 서비스 하나 바꾸려고 ISP 전체를 다시 제출하는 흐름이 된다 — 갱신 주기가 다른 데이터를 한 문서에 억지로 묶는 셈이다."
- 사회복지사 대표(재고 후): "그 말을 들으니 나눠져 있는 게 맞다. 대신 ISP 화면에서 최신 서비스 현황이 바로 보이면 체감상 하나처럼 느껴질 것 같다."

**결론**: **DB 구조는 분리 유지.** 이미 존재하는 `/records/service-status` 화면을 ISP 상세 화면에서 더 눈에 띄게 연결(진입 링크 강화)하는 UX 작업만 백로그 등록 — 스키마·record_type 변경 없음.

### 3-2. TRA-001 vs EDU-005 — 분리 유지, 소프트 링크로 연속성 확보

안건 2-2에서 이미 결론. 두 record_type이 완전히 다른 작성 주체(학교/복지기관)·다른 활성 시기(청소년기/성인기)를 갖는다는 점을 존중해 **분리 유지**하되, person_id 기반 소프트 링크로 "따로 쓰지만 이어 보이게" 한다.

### 3-3. EDU-003 vs EDU-004(FBA) — 병합

안건 2-1에서 이미 결론. 필드 추가로 해소, 별도 record_type 없음.

### 3-4. LEG-001 vs LEG-003(재산목록보고서) — 병합

안건 2-4에서 이미 결론. `report_kind` 판별 필드로 해소.

## 4. 안건 4 — 기록 방식(작성 방식) 전반 원칙

**역할별 입력 방식 원칙**

| 역할 | 원칙 | 근거 발언 |
|---|---|---|
| 당사자 | 텍스트 최소화, 음성·사진·아이콘 선택 우선 | 당사자 대표: "타이핑이 제일 힘들다. 누르고 녹음하는 게 훨씬 쉽다." |
| 보호자 | 당사자 대리 작성 시 당사자용 UI를 그대로 재사용(별도 학습 불필요) | 보호자 대표: "대신 쓸 때 또 다른 화면을 배우고 싶지 않다." |
| 활동지원사 | 시간 자동계산 유지, 반복 입력 항목은 자동완성/최근값 우선 노출 | 활동지원사 대표: "매번 같은 걸 다시 고르는 게 제일 번거롭다." |
| 특수교사 | 공식문서(IEP/BIP/ITP)는 다단계 위자드 유지, 일상 관찰기록은 태그 클릭 위주로 최대한 빠르게 | 특수교사 대표: "관찰기록은 쉬는 시간에 잠깐 쓰는 거라 타이핑할 시간이 없다." |
| 사회복지사 | 다건 관리용 목록형 대시보드 + 위자드, 회의록류는 위자드 대신 단일 폼 | 사회복지사 대표: "위자드가 매번 4단계씩이면 여러 건 처리할 때 피곤하다. 로그성 기록은 짧게 끝나야 한다." |
| 치료사 | 정량 점수(domain_scores)는 선택 입력으로, 3열 비교뷰는 유지 | 치료사 측 의견: "평가 도구가 없는 영역까지 숫자를 강제하지 말아달라." |

**공통 원칙 (전원 합의)**
1. **확인(confirmation) 절차는 공식·법정 서류에만.** 새 record_type을 추가할 때도 "이게 정말 법정·공식 서류인가"를 먼저 따져 requires_confirmation 여부를 정한다 — 일상 기록에 확인 절차를 붙이면 알림 피로만 커진다는 점은 이전 라운드(2026-07-15 permission_expiry 관련 논의)에서도 이미 확인된 원칙이라 이번에도 그대로 따른다.
2. **새 record_type보다 기존 스키마 확장을 먼저 검토.** 이번 워크숍에서 후보 6건 중 2건(FBA, 재산목록보고서)이 "새 유형"이 아니라 "기존 유형의 필드 추가"로 해소된 것이 이 원칙의 실제 사례다.
3. **화면 개수를 늘리지 않고 체감 편의성을 올리는 방법을 먼저 찾는다.** WEL-004/005는 스키마를 합치지 않고 화면 연결만 강화하는 것으로 결론 났다 — "불편하다"는 신호가 항상 "합쳐야 한다"는 뜻은 아니다.
4. **역할 간 인계는 FK가 아니라 person_id 소프트 링크로.** TRA-001↔EDU-005, TRA-001↔EDU-001.transition_plan 모두 이 패턴을 따른다 — 이미 코드베이스 전반의 관행과 일치.

## 7. Wave 2-2 진행 중 발견한 선재 RLS 갭 (2026-07-17)

EDU-005 qa-verifier 검증에서 실제 `authenticated` 세션 시뮬레이션(로컬 Supabase, teacher1 계정)으로 라이브 재현한 결과, **`persons_select` RLS 정책에 permissions 보유 전문가 분기가 없어** 다음 2가지가 깨져 있었다 — EDU-005만의 문제가 아니라 BIP·IEP·ISP·LEG-001/002·TRA-001·WEL-006 전부에 이미 존재하던 선재 결함이다.

1. **"담당 당사자 목록" 조회가 전문가에게 항상 빈 목록으로 보임.** `getBipClients`/`getLegClients`/`getTransitionPlanClients`/`getIspClients`/`getItpClients` 모두 `records_select`는 통과하지만 `persons.full_name`/`birth_date`를 읽는 `persons_select`에서 막혀 목록 자체가 비어 보였다. 실측: teacher1(EDU edit 권한 보유)이 담당 학생 2명을 `persons`에서 SELECT → 0 rows.
2. **확인주체(`confirmer_id`)가 전문가 작성 기록에서 계속 NULL.** `assign_record_confirmer()` 트리거가 SECURITY INVOKER(`prosecdef=false`)라 전문가가 제출한 기록에서 트리거 내부 `persons` 조회가 같은 이유로 실패 — 보호자가 작성한 기록만 우연히 정상 동작했다(보호자는 `persons_select`를 guardians 분기로 통과).

**왜 이전 라운드(LEG 97%, BIP 등)에서 안 걸렸나**: 이전 QA 라운드들은 INSERT 성공 여부(RLS `records_insert` 통과)는 실제 role 세션으로 검증했지만, "목록 조회"·"확인주체 세팅" 같은 **읽기 경로의 실제 authenticated 세션 결과**까지는 재현하지 않고 정적 정책 검토나 superuser 경로로 대체한 경우가 있었다 — 이번 EDU-005 검증에서 처음으로 `SET LOCAL role authenticated` + JWT claim 시뮬레이션으로 실제 세션을 재현해 드러났다.

**조치**: `supabase/prisma/migrations/20260717130000_p3_persons_select_permission_holders/`로 `persons_select`에 활성 `permissions` 보유자 분기 추가(records_select와 동형 패턴). 라이브 재현으로 teacher1의 persons SELECT(0→2 rows)·EDU-005 INSERT 시 `confirmer_id` 정상 세팅을 재검증 완료. `supabase/tests/01_persons.sql`에 회귀 방지 assert 추가(plan 9→10) 후 클린 스키마에서 단독 실행해 통과 확인(pgTAP 하네스의 fixture 이메일 충돌 버그로 파일 전체 완주는 안 됐지만 신규 assert 자체는 "ok" 확인).

**후속 권고**: 이 갭은 EDU-005 하나만의 문제가 아니었으므로, 기존에 이미 배포된 BIP·IEP·ISP·LEG·TRA·WEL-006의 "담당 당사자 목록" 화면들이 실제 프로덕션에서도 정상 동작하는지(개발 중엔 seed 데이터를 superuser로 만들어 눈치채기 어려웠을 가능성) 한 번은 실 사용자 세션으로 스팟체크할 것을 권장한다.

**✅ 스팟체크 완료(2026-07-18)** — `SET LOCAL role authenticated` + JWT claim 시뮬레이션으로 실제 전문가 세션 5종을 전수 재현:

| 역할 | 담당 당사자 목록(persons SELECT) | 확인주체(confirmer_id) 세팅 |
|---|---|---|
| teacher1 (EDU edit) | 2 rows ✅ | EDU-005 → 정상 세팅 ✅(전날 검증) |
| therapist1 (MED edit) | 2 rows ✅ | MED-005 INSERT → 정상 세팅 ✅ |
| supporter1 (DAI write) | 2 rows ✅ | (DAI는 requires_confirmation 없음 — 목록 조회만 해당) |

5개 역할 전부, 그리고 EDU-005 포함 5개 record_type(MED-005/WEL-004/TRA-001/LEG-001/EDU-005) 전부에서 확인주체가 실제 담당 보호자(a...002)로 정확히 세팅됨을 확인 — `persons_select` 수정이 EDU-005 하나가 아니라 **전체 전문가 역할·전체 공식문서 record_type에 일괄 적용**됨을 실측으로 확정했다. 모든 검증은 트랜잭션 ROLLBACK으로 진행해 시드 데이터에 영향 없음.
