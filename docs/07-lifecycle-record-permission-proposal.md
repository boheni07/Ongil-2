## 1. 왜 3단계에서 5단계로 바꾸나

v0.1에서 이미 지적했던 갭 중 두 가지가 **생애주기 모델 자체의 해상도 부족**에서 비롯된 구조적 문제였다.

- 현장은 아동기를 **영유아기(0~5세)/아동기(6~12세)**로 나누는데, 온길은 "만 13세 이하"를 통째로 `child` 하나로 묶는다 — 조기개입(영유아기)과 학교생활(아동기)은 정책 영역과 이해관계자가 크게 다르다.
- 현장은 성인기 이후를 **성인기(19~64세)/노년기(65세 이상)**로 나누는데, 온길은 "만 18세 이상"을 통째로 `adult` 하나로 묶는다 — 취업·자립(성인기)과 돌봄·후견감독(노년기)은 완전히 다른 지원 성격이다.

이 두 문제는 record_type 신설이나 필드 보강만으로는 해결되지 않는다 — **생애주기 단계 자체를 나눠야** 확인주체·주도 도메인·화면 배지가 실제 필요에 맞게 갈라진다. 그래서 이번 버전은 생애주기 모델을 현장의 5단계에 맞춰 재설계한다.

## 2. 제안하는 생애주기 5단계 정의

| 단계 | 코드(제안) | 연령 기준 | 근거 | 기존 3단계 대응 |
|---|---|---|---|---|
| **영유아기** | `infant` | 만 0~5세(미취학) | 조기 진단·개입이 결정적 시기(현장 조사) | `child`의 앞부분 (신규 분리) |
| **아동기** | `child` | 만 6~12세(초등 학령기) | 학교생활 적응, 특수교육 학령기 대상 | `child`의 뒷부분 |
| **청소년기(전환기)** | `youth` | 만 13~18세 | 기존 온길 설계와 동일(전환교육 시기) | `youth` 그대로 유지 |
| **성인기** | `adult` | 만 19~64세 | **민법상 성년(만 19세)**과 일치 — 기존 온길의 "만 18세"는 특수교육 지원 상한(교육행정 기준)과 성년후견 등 법적 성년 기준을 혼용하고 있었다. 19세로 올리면 LEG 도메인(후견) 정합성이 개선된다 | `adult`의 앞부분, **경계값 18→19로 정정** |
| **노년기** | `senior` | 만 65세 이상 | 노인복지법상 노인 기준과 일치, 건강관리·돌봄 성격 전환 | `adult`의 뒷부분 (신규 분리) |

> ⚠️ **경계값 변경 주의**: 기존 온길은 "성년기 = 만 18세 이상"이었다. 이번 제안은 이를 **만 19세**로 올린다(민법 기준 정합). 그 결과 **만 18세인 당사자**는 기존 설계에서는 `adult`(본인 확인주체)였지만, 이번 제안에서는 `youth`(보호자 확인주체)로 바뀐다 — 채택 시 실사용자 영향이 있는 변경이므로 별도 공지가 필요하다.

## 3. 스키마·코드 영향 범위

생애주기는 저장 컬럼이 아니라 `birth_date` 기반 계산값이므로(`05-erd.md` §2-2-1), 마이그레이션 없이 **함수 로직 변경만으로 반영 가능**하다.

```sql
CREATE OR REPLACE FUNCTION get_life_stage(p_birth_date date)
RETURNS text LANGUAGE sql STABLE AS $$
  SELECT CASE
    WHEN date_part('year', age(p_birth_date)) >= 65 THEN 'senior'  -- 노년기
    WHEN date_part('year', age(p_birth_date)) >= 19 THEN 'adult'   -- 성인기 (기존 18→19 상향)
    WHEN date_part('year', age(p_birth_date)) >= 13 THEN 'youth'   -- 청소년기(전환기), 기존과 동일
    WHEN date_part('year', age(p_birth_date)) >= 6  THEN 'child'   -- 아동기 (기존 13이하→6~12로 축소)
    ELSE 'infant'                                                   -- 영유아기 (신규)
  END;
$$;
```

**영향받는 지점** (현재 코드베이스 기준, 실제 확인됨):

| 지점 | 현재 로직 | 변경 필요 |
|---|---|---|
| `assign_record_confirmer()` 트리거(`05-erd.md` §4-6②) | `IF v_stage = 'adult' THEN 본인 ELSE 보호자` | 그대로 유지 가능 — `'adult'` 또는 `'senior'`면 본인, 그 외는 보호자로 조건만 `IN ('adult','senior')`로 확장 |
| `users.deactivated_at`/`is_adult` 트리거(Flow-SYS-05, 매일 cron) | 만 18세 도달 시 `is_adult=true` | **경계값 19세로 정정** — 채택 시 가장 민감한 변경점 |
| `apps/web/src/components/teacher/IepWizard.tsx:98` | `student.lifeStage !== "child"` | `'infant'`도 이제 별도 값이므로 조건은 `!== 'infant' && !== 'child'`로 명시(현행 로직이 `child` 외 전부 허용이라 사실상 그대로 작동하지만, 값 목록이 늘어난 만큼 테스트 재확인 필요) |
| `apps/web/src/components/teacher/IepWizard.tsx:548` | `lifeStage === "adult" ? 본인 : 보호자` | `['adult','senior'].includes(lifeStage) ? 본인 : 보호자` |
| `StageBadge` 컴포넌트(`03-uiux.md` §6-6) | child/youth/adult 3색 | **영유아기·노년기 2개 색상·아이콘 추가 필요** |
| `docs/02-ia.md` §3-9 화면 목록(G-01/G-10/G-30/P-01/T-01/T-13/T-20/W-01/W-16/W-20/TH-20) | 3단계 조건문 | 전부 5단계 조건으로 재검토 필요(가장 넓은 영향 범위) |
