# 12. 콘텐츠 정합성 워크숍 — 프로토타입 카드 내부 구조·타이포그래피 대조

**작성일**: 2026-07-19
**계기**: "화면이 존재하는가/메뉴가 맞는가" 수준까지는 이번 세션 앞선 라운드(`docs/09` CTO 갭분석 후속, `_workspace/11_prototype_gap_analysis.md` + Wave 1/2/P3)에서 웹·모바일 모두 정리됐다. 그런데 사용자가 보호자 대시보드(G-01)를 구체 예시로 들며 지적한 것은 그보다 한 단계 더 세밀한 층위 — **화면은 있지만 그 안의 카드가 실제로 프로토타입과 같은 콘텐츠 구조(어떤 항목을 몇 개, 어떤 순서로, 어떤 라벨로)를 보여주고 있는가, 줄간격·폰트크기 같은 타이포그래피까지 맞는가**였다. 이 문서는 그 정밀도로 새로 진행한 워크숍 결과다.

## 1. 참여 구성 (시뮬레이션)

**기술팀**: PM · PL · UIUX전문가 · 디자이너 · 퍼블리셔 · 프론트엔드개발자 · 시니어개발자
**사용자팀**: 당사자 1명 · 보호자 2명(단일 자녀/다자녀) · 특수교사 · 사회복지사 · 치료사 · 활동지원사 각 1명

## 2. 방법론

기존 `_workspace/11_prototype_gap_analysis.md`는 "이 화면이 존재하는가 / 이 버튼이 있는가"를 물었다. 이번엔 화면 하나(G-01)를 **완전히 해부**하는 방식을 채택했다 — 프로토타입 HTML·CSS 원문(선택자 단위)과 실제 컴포넌트 코드를 나란히 놓고, 카드마다 ① 어떤 데이터 항목이 노출되는가 ② 각 항목의 순서 ③ 라벨 문구 ④ 타이포그래피(font-size·color·spacing) ⑤ 하단 CTA 문구·목적지 다섯 축으로 대조했다. 이 정밀도를 G-01에서 확립한 뒤, 같은 방법을 다른 역할의 홈 화면(구조가 유사한 "요약 카드 그리드" 패턴을 쓰는 화면들)에도 적용할 수 있도록 체크리스트화했다.

## 3. Exhibit A — G-01 보호자 대시보드 정밀 대조

### 3-1. 당사자 카드(person-card) 상단 통계

| 항목 | 프로토타입(`web-guardian.html` 300~304줄) | 실제 구현(`PersonSlider.tsx` `PersonCard`) |
|---|---|---|
| 이번주 기록 수 | `<b>12</b><span>이번주 기록</span>` | **없음** |
| 권한 부여 건수 | `<b>4</b><span>권한 부여</span>` | **없음** |
| 다음 공식문서 점검 D-day | `<b>D-14</b><span>IEP 점검</span>` | **없음** |

**갭**: 당사자 카드에 이름·생년월일·나이·성별·장애유형 칩만 있고, 프로토타입의 핵심인 3항목 통계 바(`pc-stats`)가 통째로 빠져 있다. 카드를 봐도 "이 아이가 요즘 어떤 상태인지" 숫자로 감이 안 온다.

**타이포그래피**(`.pc-stat b{font-size:18px}`, `.pc-stat span{font-size:11px}`): 큰 숫자 18px 굵게 + 11px 회색 라벨, 카드형 배경(`--bg`, 8px 패딩) 3등분 가로배치.

### 3-2. "최근 기록" 카드

| 항목 | 프로토타입 | 실제 구현 |
|---|---|---|
| 도메인 칩 | ✅ `<span class="chip d-MED">의료</span>` | ✅ `<DomainChip domain={r.domain} />` |
| **기록명**(제목) | ✅ `<b>재활의학과 정기 진료</b>` (실제 문서 제목) | ❌ `record_type` 코드값 텍스트로 대체(예: "MED-006") |
| **작성자** | ✅ `이재활 · ` | ❌ 없음 |
| 작성일시(상대표기) | ✅ `오늘 10:30` / `어제` / `2일 전` | ⚠️ `YYYY-MM-DD` 절대날짜만 |
| 하단 CTA | `전체 기록 보기` → G-20 | `전체 기록 보기 →` → `/persons/{id}/records` (일치) |

**갭 근본원인**: `getPersonSummaryCards()`(dashboard/actions.ts)의 `recentRecords` 쿼리가 `id, domain, record_type, record_date`만 select하고 `content`(제목 파생용)와 `author_id→users.full_name`을 가져오지 않는다. `record_type` 코드를 그대로 화면에 찍는 건 애초에 사람이 읽을 이름이 아니다 — 다행히 `recordDisplayTitle(recordType, content)`(`packages/validation/src/records.ts`)가 이미 있어 재사용만 하면 된다.

### 3-3. "권한 현황" 카드

| 항목 | 프로토타입 | 실제 구현 |
|---|---|---|
| 권한 보유자 **목록**(이름·역할·수준 배지) | ✅ 4행 리스트, `읽기`/`작성`/`편집` 색상 배지 | ❌ **숫자 하나만**(`permissionCount`) |
| 하단 CTA | `권한 매트릭스` → G-30 | `권한 매트릭스 보기 →` (일치) |

**갭**: 가장 큰 정보 손실 구간. "권한을 몇 명에게 줬는지"만 보이고 "누구에게 어떤 수준으로 줬는지"가 대시보드에서 안 보여서, 확인하려면 무조건 권한 매트릭스 화면까지 들어가야 한다. `permissions` 테이블에서 `grantee_id→users.full_name/role`, `access_level`을 join하는 쿼리 자체는 이미 다른 화면(PermissionMatrix)에 있는 패턴 재사용으로 충분하다.

**타이포그래피**: `.perm-row{font-size:13px}`, 수준 배지는 `읽기`(파란)/`작성`(초록)/`편집`(주황) 3색 pill(`border-radius:999px`).

### 3-4. "알림" 카드

| 항목 | 프로토타입 | 실제 구현 |
|---|---|---|
| 알림 **목록**(제목+설명 2줄) | ✅ 3행 | ❌ 링크 텍스트 하나뿐 |
| 하단 CTA | `권한 부여하기`(amber) → G-32 | `알림함 보기 →` |

**⚠️ 프로토타입 자체의 모순 발견**: 이 카드 제목이 "알림"인데 하단 버튼이 "권한 부여하기"(G-32)로 가는 건 프로토타입 원본의 복붙 실수로 보인다(알림과 권한부여는 무관한 플로우). **사용자가 이번 요청에서 직접 "알림함 보기"를 지정**했으므로, 목록은 프로토타입대로 실제 알림 3건을 보여주되 CTA는 프로토타입 원문이 아니라 사용자 지시(`알림함 보기` → `/notifications`)를 채택한다 — 유일하게 프로토타입 원문을 그대로 안 따르기로 한 지점이며, 근거는 명시했다.

**데이터 소스**: `notifications` 테이블은 `recipient_id`(로그인 계정) 기준이라 당사자별로 나뉘지 않는다 — 프로토타입 예시도 특정 당사자에 종속되지 않은 알림들이라 일치. `getUnreadNotificationCount()`와 동일한 조회 경로에 `getRecentNotifications(limit)` 하나만 추가하면 된다(신규 쿼리 아님, 기존 함수 옆 자매 함수).

### 3-5. "확인 대기 기록" 카드

| 항목 | 프로토타입 | 실제 구현(`PendingConfirmCard.tsx`) |
|---|---|---|
| 기록 **목록**(도메인 칩+기록명+작성자+제출일시+확인대기 배지) | ✅ 2행 | ❌ **"N건이 있습니다" 문장 하나** |
| 안내 문구("승인·반려 아닌 확인 절차") | ✅ | ✅(문구는 이미 있음) |
| 하단 CTA | `기록 관리에서 확인하기` → G-20 | `확인하러 가기 →` (문구만 다름, 목적지는 동일) |

**갭**: 여기도 건수만 알려주고 "무엇이" 대기 중인지는 안 보여준다. `pendingConfirmationCount`를 세는 쿼리를 `records.select("id, domain, record_type, content, author_id, record_date")...eq("requires_confirmation", true).is("confirmed_at", null)` 형태의 목록 쿼리로 바꾸면 count는 `.length`로 파생 가능(쿼리 통합, 오히려 단순화).

## 4. 타이포그래피·스페이싱 체크리스트(프로토타입 원문 값)

퍼블리셔가 카드 내부 리스트 구현 시 참고할 raw 값(전부 `web-guardian.html` CSS 원문):

| 요소 | 값 |
|---|---|
| 카드 컨테이너 | `padding:16px`, `border-radius: var(--br-md)`, `border:1px solid var(--bd)` |
| 카드 제목(`.ch`) | `font-size:16px`, `margin-bottom:12px` |
| 리스트 행(`.rec-row`) | `padding:10px 0`, `border-bottom:1px solid var(--bd)`(마지막 행 제외), `gap:10px`, 아이템 정렬 `flex-start` |
| 행 제목(`.rt b`) | `font-weight:600`(제목은 세미볼드, 익스트라볼드 아님 — 현재 다른 화면에서 자주 쓰는 `font-extrabold`보다 약함, 과도한 굵기 지양) |
| 행 부제(`.rd`) | `font-size:12px`, `color:var(--muted)` |
| 권한 행(`.perm-row`) | `padding:9px 0`, `font-size:13px` |
| 인물 카드 통계 숫자(`.pc-stat b`) | `font-size:18px`, `color:var(--primary-700)` |
| 인물 카드 통계 라벨(`.pc-stat span`) | `font-size:11px`, `color:var(--muted)` |
| 하단 CTA 버튼 | 카드 폭 100%, `margin-top:12px`, "알림" 카드만 `btn-amber`(강조), 나머지는 `btn-ghost`(보조 톤) |

이 표는 이번 워크숍에서 확립한 **"카드 내부 리스트" 공통 스펙**이다 — G-01 이외에 같은 패턴(요약 카드 + 목록 + 하단 CTA)을 쓰는 다른 역할 홈 화면에도 그대로 적용한다.

## 5. 확장 적용이 필요한 다른 화면

같은 "요약 카드 + 목록 + CTA" 패턴을 쓰는 화면들 — 이번 세션 Wave 1/2에서 일부(사회복지사 "오늘 할 일")는 이미 이 정밀도로 손을 댔지만, 나머지는 화면 단위 존재만 확인했지 카드 내부까지는 이번 워크숍 수준으로 대조하지 않았다:

- **T-01**(특수교사 홈): 담당 학생 카드 내부 통계 구성이 G-01의 `pc-stats`와 동일 패턴인지 미대조.
- **TH-01**(치료사 홈), **S-01**(활동지원사 홈): 오늘 일정 카드는 백엔드 부재로 별도 트랙이지만, 그 외 요약 카드(담당 아동 통계 등)는 미대조.
- **W-01**(사회복지사 홈): "오늘 할 일"은 이미 반영했으나 "담당 당사자" 카드 자체의 통계 항목 구성은 미대조.
- **G-10**(생애주기 타임라인): "이정표"(milestone) 강조 카드 스타일 미대조.

## 6. 개선 계획

**Wave A — 백엔드(데이터 확장, `dashboard/actions.ts`)**
1. `getPersonSummaryCards`의 `recentRecords`에 `content`(→`recordDisplayTitle`)·`author_id→full_name` 추가, 날짜를 상대표기 헬퍼로 변환.
2. `permissions` **목록**(수여자 이름·역할·access_level, 최대 5건) 반환 필드 신설.
3. `pendingConfirmation`을 count가 아닌 **목록**(도메인·제목·작성자·제출일시) 반환으로 교체.
4. `getRecentNotifications(limit=3)` 신설(기존 `getUnreadNotificationCount`와 같은 위치).
5. 당사자 카드 상단 통계 3종(이번주 기록 수 / 권한 부여 건수 / 다음 공식문서 점검 D-day) 산출 — ⚠️ **D-day 정의는 설계 결정 필요**: 프로토타입은 "IEP 점검"·"치료 회기"처럼 당사자마다 다른 기준을 쓴다. 이 프로젝트엔 이미 도메인별로 "다음 검토일"류 필드(IEP는 없음, ISP `reassessment_date`, 전환계획 `next_review_date`, ITP `next_review_date`)가 흩어져 있어, 당사자별로 "그 당사자에게 활성화된 도메인 중 가장 임박한 다음 검토일"을 고르는 로직이 필요하다. PM·PL 확인 후 착수 권장.

**Wave B — 프론트엔드(`PersonSlider.tsx`, `PendingConfirmCard.tsx` 재구성)**
1. `PersonCard`에 `pc-stats` 3열 통계 바 추가.
2. "최근 기록"·"권한 현황"·"알림" 3카드를 실제 목록 렌더링으로 교체(§4 타이포그래피 체크리스트 적용).
3. `PendingConfirmCard`를 목록형으로 재작성, CTA 문구를 "기록 관리에서 확인하기"로 통일(현재 "확인하러 가기"와 목적지는 같음, 문구만 프로토타입 일치).
4. "알림" 카드 CTA는 프로토타입 원문(`권한 부여하기`)이 아니라 사용자 지시(`알림함 보기` → `/notifications`)를 채택 — §3-4 근거 유지.

**Wave C — 확장 적용**
§5에서 나열한 나머지 홈 화면들에 동일 정밀도(§2 방법론, §4 체크리스트)로 재대조 후 필요분 반영. 모바일은 웹 확정 후 동일 원칙으로 포팅(이번 세션 관행과 동일).

## 7. 결정 대기 항목 (사용자 확인 필요)

- Wave A-5의 "다음 공식문서 점검 D-day" 산출 기준 — 도메인별 필드가 흩어져 있어 통일 규칙 확정 필요.
- "알림" 카드 CTA를 프로토타입 원문 대신 사용자 지시로 덮어쓴 것 — 이견 없으면 그대로 진행.
- Wave C 확장 범위 — 4개 화면(T-01/TH-01/S-01/W-01) 전부 이번 라운드에 포함할지, G-01만 먼저 완결하고 나머지는 후속으로 미룰지.

이번 문서는 계획까지다 — Wave A/B 구현은 사용자 확인 후 착수한다.
