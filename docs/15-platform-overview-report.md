## 2. 왜 온길인가 — 핵심 가치와 문제의식

### 2-1. 세 가지 핵심 가치

| 가치 | 설명 |
|---|---|
| 당사자 중심 | 모든 기록의 주인은 당사자 본인이며, 이해관계자(보호자·전문가)는 허락받은 범위 안에서만 접근한다 |
| 안전한 공유 | PostgreSQL 행 수준 보안(RLS)으로 도메인·역할별 접근을 데이터베이스 레벨에서 강제한다 — 애플리케이션 코드가 실수해도 DB가 마지막 방어선이 된다 |
| 생애주기 연속성 | 의료·교육·복지·일상·전환·법률 6개 도메인에 흩어지기 쉬운 기록을 하나의 통합 타임라인으로 조회할 수 있다 |

### 2-2. 해결하려는 문제

장애인의 생애 기록은 통상 기관·서비스별로 단절돼 있다 — 특수학교의 IEP, 복지관의 ISP, 병원·치료실의 치료계획서, 활동지원기관의 일지, 성년후견 관련 법률 문서가 각각 다른 시스템이나 종이 문서로 흩어진다. 보호자는 여러 창구를 오가며 같은 정보를 반복 설명해야 하고, 당사자 본인은 정작 자신에 대한 기록에 접근하기 어렵다.

온길은 이 기록들을 **하나의 플랫폼, 하나의 타임라인**으로 모으되, 소유권은 명확히 당사자에게 두고 각 이해관계자는 필요한 범위만 접근하도록 세밀하게 통제한다. 이 통제는 UI 상의 약속이 아니라 PostgreSQL RLS로 데이터베이스 레벨에서 강제된다.

## 3. 사용자와 생애주기

### 3-1. 6개 사용자 역할

| 역할 코드 | 역할명 | 주요 목적 |
|---|---|---|
| `person` | 당사자 | 자기 기록 확인 및 자기표현, 접근 권한 관리 |
| `guardian` | 보호자 | 복수 당사자 기록 관리, 이해관계자 권한 부여 |
| `supporter` | 활동지원사 | 활동지원 일지 작성, 인계인수 확인 |
| `teacher` | 특수교사 | IEP 작성·점검, 관찰기록·행동중재계획(BIP)·개별화전환계획(ITP) 작성 |
| `social_worker` | 사회복지사 | ISP 작성·점검, 전환계획 로드맵, 후견·권익옹호 기록, 사례회의록 관리 |
| `therapist` | 치료사 | 치료계획서·회기일지·평가보고서 작성 |

당사자는 "셀프 가입" 모델도 지원한다 — 스스로 가입한 당사자는 `persons.id = primary_guardian_id = auth.uid()`로 자기 자신이 곧 자기 행의 주보호자가 되는 구조를 취해, 대리 등록 없이도 전체 플랫폼 기능을 동일하게 사용할 수 있다.

### 3-3. 생애주기 5단계 (`life_stage`)

당사자의 생년월일을 기준으로 서버가 계산하는 파생 상태로, 도메인별 기록 활성화 시점과 **동의 주체**를 결정한다. 최초 3단계(아동기/청소년 전환기/성년기) 설계에서 실제 특수교육·장애복지 현장의 구분에 맞춰 5단계로 확장했다(성년 경계도 만 18세 → 만 19세로 상향, 민법상 성년 기준과 정합).

| 단계 | 연령 기준 | 당사자 상태 변화 | 주요 기록대상 | 주도 도메인 |
|---|---|---|---|---|
| 영유아기 (`infant`) | 만 0~5세 | 보호자 대리동의 전체 | 진단·조기개입·재활치료, 관찰기록(만 3세~) | MED·WEL·DAI |
| 아동기 (`child`) | 만 6~12세 | 보호자 대리동의 전체 | IEP 기본 5영역, 관찰기록, 활동지원 일지, 자기표현 | MED·EDU·DAI·WEL |
| 청소년 전환기 (`youth`) | 만 13~18세 | 전환계획 수립 개시 | 전환 목표영역·희망 진로·전환 활동계획·연계기관 | MED·EDU·DAI·WEL·TRA |
| 성인기 (`adult`) | 만 19~64세 | **동의 주체가 보호자→본인으로 이관** | 본인 동의 재취득, 성인 ISP, 전환 로드맵 실행, 후견·권익옹호 | WEL·TRA(실행)·LEG |
| 노년기 (`senior`) | 만 65세 이상 | 동의 주체는 계속 본인 | 돌봄 성격 강화, 만성질환 관리, 후견감독 관련 지원 밀도 증가 | WEL·LEG·MED |

이 계산값은 화면 곳곳의 `StageBadge`로 시각화되고, 타임라인의 단계 전환 시점(만 6·13·19·65세) 구분선, 위자드의 전환계획 섹션 잠금 해제 조건, 확인 절차의 확인 주체(§3-5) 판정에도 그대로 쓰인다.

## 4. 기록 체계 — 16종 record_type

온길의 모든 기록은 단일 `records` 테이블에 `domain`(6종)과 `record_type`(16종)으로 저장되고, 실제 내용은 `content` JSONB 컬럼에 유형별 스키마(Zod, `packages/validation/src/records.ts`)로 검증돼 담긴다. record_type은 DB CHECK 제약이 아닌 자유 text이므로, 새 기록 유형을 마이그레이션 없이 신속하게 추가할 수 있는 것이 이 설계의 핵심 이점이다(실제로 EDU-005·WEL-006 2종이 이 방식으로 마이그레이션 없이 추가됐다).

| DAI | SELF-001 | 자기표현 — 기분·식사·활동·건강 상태를 당사자가 스스로 남기는 일일 기록 | 당사자(본인), 보호자 대리 가능 | 보호자·활동지원사·특수교사·치료사 |

| 무관 | GEN-001 | 보호자 범용 기록 — 도메인 제한 없는 자유형식 메모 | 보호자 | 당사자(해당 시) |

보조작성자(주작성자가 아니면서 예외적으로 쓸 수 있는 경로)가 존재하는 유형은 SELF-001(보호자 대리 작성, `author_id`는 항상 보호자로 위조 방지 고정)과 TRA-001(특수교사, 청소년기 이상+TRA 권한 보유 시 조건부) 2개뿐이며, 나머지 14개는 한 역할이 전담 작성한다.

LEG-001/002는 서버·클라이언트 양쪽에서 "성인기·노년기(만 19세 이상)"라는 연령 가드를 이중으로 검증한다 — 이 가드가 최초 구현 시 누락됐던 사고가 있었고(영유아기 당사자에게도 후견감독보고서 작성이 가능했던 결함), 발견 즉시 수정하며 이후 신규 기록 유형에도 동일 원칙을 명문화해 재발을 막았다.

## 5. 권한 모델 — "허락받은 범위만"

### 5-1. 두 층위의 접근 경로

| 경로 | 대상 | 특징 |
|---|---|---|
| **구조적 접근** | 보호자 ↔ 자신이 등록한 당사자 | `guardians` 관계 테이블 기반, 도메인·기록유형 무관하게 항상 전체 접근. `permissions` 테이블 부여 여부와 무관 |
| **동적 권한 부여** | 전문가(교사·사회복지사·치료사·활동지원사) ↔ 담당 당사자 | 보호자가 `permissions` 테이블에 도메인 단위로 `read`/`write`/`edit` 중 하나를 명시적으로 부여. 유효기간(`valid_until`) 설정 가능, 자동 만료 |

### 5-2. 역할별 권한 프리셋(위자드 기본값)

| 역할 | 의료 MED | 교육 EDU | 복지 WEL | 일상 DAI | 전환 TRA | 법률 LEG |
|---|:---:|:---:|:---:|:---:|:---:|:---:|
| 활동지원사 | read | – | – | **write** | – | – |
| 특수교사 | – | **edit** | – | read | **write**(만 13세+만 조건부) | – |
| 사회복지사 | read | – | **edit** | – | **write** | read |
| 치료사 | **edit** | – | – | read | – | – |
| 당사자 | read(본인) | read(본인) | read(본인) | write(자기표현) | read(본인) | read(본인) |
| 보호자 | 전체(구조적) | 전체 | 전체 | 전체 | 전체 | 전체 |

권한 판단은 **도메인 단위**로만 이뤄지며, record_type 단위 세분화는 데이터베이스가 아니라 애플리케이션 레이어(화면별 작성 폼 + Zod 스키마)가 책임진다는 점이 이 설계의 중요한 특징이다.

### 5-3. 권한 라이프사이클

| 단계 | 트리거 | 처리 |
|---|---|---|
| 부여(Grant) | 보호자가 4단계 위자드 완료 | 프리셋 자동 채움(수정 가능) → `permissions` INSERT + `permission_logs` 기록 → 대상자 알림 |
| 수정(Modify) | 권한 매트릭스에서 도메인별 일괄 수정 | diff를 `permission_logs`에 불변 기록, 상향 변경 시만 대상자 알림 |
| 즉시 회수(Revoke) | 보호자가 회수, 계약종료·이해상충 발생 | `is_active=false` 즉시 반영 → RLS 즉시 재평가 |
| 자동 만료(Expiry) | `valid_until` 도래 | 매일 pg_cron 배치가 만료 대상 스캔·일괄 회수, D-7 시점 사전 경고 배지 |
| 감사(Audit) | 정기 | `permission_logs` × `access_logs` 교차 조회로 미사용·과다 권한 탐지 |

**정책 가드레일**: `edit` 수준은 항상 유효기간 필수(무기한 지양), 모든 변경은 불변 로그로 남고, 회수는 캐시 무효화와 원자적으로 처리된다.

### 5-4. 기록 확인(Confirmation) 절차 — "승인"이 아니라 "확인"

전문가가 IEP·ISP·치료계획서 등 공식 문서를 작성·완성하는 권한 구조는 그대로 유지하되, 보호자·당사자가 그 존재와 내용을 **인지했음을 남기는 절차**를 별도로 둔다. 반려·차단 기능은 의도적으로 없다 — 이견이 있으면 별도 정정 요청 경로(인계인수·알림)를 쓴다.

- 확인 주체는 생애주기 단계 기준: 아동기·청소년 전환기는 주보호자, 성인기 이상은 본인(당사자) — 자기결정권을 반영한 설계.
- 확인 대기 상태여도 기록은 이미 확정 상태이며 열람·활용에 제약이 없다 — 확인은 참고용 상태 표시일 뿐이다.
- 기록이 수정되면 확인 상태가 초기화돼 재확인이 필요해진다.

## 6. 보안 아키텍처 — RLS를 최종 방어선으로

### 6-1. 설계 원칙

온길의 모든 접근 통제는 애플리케이션 코드가 아니라 **PostgreSQL Row-Level Security(RLS)**에서 최종적으로 강제된다. Server Action은 역할을 확인하고 편의 기능을 제공하지만, 실제 데이터 접근 가부는 항상 RLS 정책이 최종 판정한다 — 즉 애플리케이션 코드에 버그가 있어도 DB가 방어선이 된다.

### 6-2. 반복적으로 발견·차단해 온 결함 패턴

이 프로젝트의 개발 이력에서 가장 중요한 교훈은 **"신규 테이블에 RLS가 활성화되지 않거나, GRANT가 과다 부여되는 결함이 8회 이상 반복됐다"**는 점이다: `guardians`, `consents`, `permission_logs`, `handover_notes`/`notifications`, `notification_preferences`/`permission_presets`, `users` 컬럼 GRANT 등에서 순차적으로 발견·핫픽스됐다. 매번 발견 즉시 봉쇄했을 뿐 아니라, 6번째 반복 이후에는 **`pg_class.relrowsecurity`를 동적으로 순회해 전 테이블의 RLS 활성화 여부를 강제하는 메타 pgTAP 테스트**(`supabase/tests/17_meta_all_tables_rls_enabled.sql`)를 신설해 신규 테이블이 추가돼도 이 결함이 자동으로 잡히도록 근본 차단했다.

이후에도 정책 간 **논리적 일관성**(예: "records를 볼 수 있으면 persons도 볼 수 있어야 한다"는 불변식) 문제가 한 차례 더 발견됐고, 이를 검증하는 별도 메타 테스트(`23_persons_records_select_consistency.sql`)도 추가했다. 현재 보안 회귀 테스트는 총 24개 pgTAP 파일로 구성돼 있으며 전체 스위트가 완주 가능한 상태다.

### 6-3. 핵심 RLS 원칙 요약

| 원칙 | 설명 |
|---|---|
| 컬럼 GRANT는 REVOKE 후 GRANT | 테이블 전체 UPDATE GRANT가 있는 상태에서 정책만 열면 위험 컬럼(예: `role`, `primary_guardian_id`)까지 수정 가능해진다 — 반드시 REVOKE 후 안전 컬럼만 재부여 |
| author_id 위조 방지 | 대리 작성(보호자가 당사자 대신 자기표현 작성 등)에서도 `author_id`는 항상 실제 작성자로 DB 레벨에서 고정 |
| 도메인 단위 강제, record_type은 앱 레이어 | RLS는 `domain`만 검사하고 `record_type` 세분화는 화면·Zod 스키마가 담당 |
| 정책 변경 시 연관 정책 교차 검토 | `records_select`가 바뀌면 `persons_select`도 함께 검토해야 한다는 교훈이 메타 테스트로 코드화됨 |

### 9-3. 반복해서 지켜온 품질 원칙

1. **신뢰 소스는 항상 실제 코드** — RLS 정책 SQL, Zod 스키마가 최종 근거이며 문서는 그 스냅샷. 정합성 검증 라운드마다 이 원칙에 따라 문서를 코드에 맞춰 갱신했다.
2. **연령 가드·위조 방지는 이중 구현** — 서버 함수 내부 재검증 + 화면 UI 가드를 항상 함께 둔다. 한 번 빠뜨렸던 사고(LEG 연령가드 누락)를 계기로 이후 모든 신규 record_type에 체크리스트화됐다.
3. **웹→모바일은 동시 또는 근접 이식** — 초기엔 웹만 개선하고 모바일이 뒤처지는 패턴이 반복됐으나, 이후 라운드부터는 "웹·모바일을 처음부터 동시 구현"하는 방향으로 전환했다.
4. **YAGNI를 지키되 반복 패턴은 관찰** — `getXxxClients` 골격 같은 반복 구현은 3곳까지는 "질서있는 패턴 재사용"으로 판단해 추상화하지 않고, 4번째 사례가 생길 때 재논의하기로 명시적으로 합의했다.
5. **결함 발견 시 메타 테스트로 근본 차단** — 동일 계열 결함이 반복될 때마다 개별 핫픽스에 그치지 않고, 그 결함군 자체를 자동으로 잡아내는 메타 회귀 테스트(전 테이블 RLS 강제, 정책 간 논리 일관성 등)를 추가해왔다.
